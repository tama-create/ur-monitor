# ur-monitor

UR賃貸の空き部屋を定期監視し、条件に合う新着があれば Slack へ通知します。

## なぜ作ったのか

**UR は、空室が出ても向こうから知らせてはくれません。** 公式の「よくあるご質問」でも、
「希望する物件に空室が出たら連絡してくれるの？」という問いに対して
「空室情報につきましては随時更新されておりますので、UR賃貸住宅Webサイトまたは店舗で
ご確認ください」と案内されています。つまり**自分で何度も見に行くしかない**、が公式の答えです。

メールで届く仕組みが皆無なわけではありません。UR には
[空室情報お届けサービス](https://www.ur-net.go.jp/chintai/akishitsu/) があり、
登録した条件に合う部屋の募集開始をメールで知らせてくれます。ただし対象は
**子育て世帯と若者夫婦世帯に限られ、実施しているのも一部の団地だけ**です。
事前の申込みとマイページでの条件登録も要ります。ここから外れる人には使えません。

そして**UR賃貸は、約70万戸のほとんどが抽選なしの先着順**です（新築物件など一部は抽選）。
気づくのが数時間遅れただけで、もう他の人に決まっていた、ということが普通に起こります。

1件を見張るだけでも大変なのに、候補が複数あればなおさら現実的ではありません。
仕事中も寝ている間も、人間が張り付き続けることはできません。

**だから、入居したい物件を横断的に監視して、空きが出た瞬間に知らせる仕組みが要ります。**
このツールはそのために作りました。5分おきに自動で見に行き、条件に合う新着だけを通知します。
見張る作業は機械に任せて、**人間は「見つけたらすぐ動く」という本当に大事な一手に集中できます。**

通知には**その部屋のページへの直リンク**が入っています。開くと「お部屋の内覧・お申込みの
お問い合わせ」欄に、担当 UR賃貸ショップの直通番号（**スマホならタップで発信**）と
「ネットで仮申込み」ボタンが並んでいます。**通知 → リンクをタップ → 電話ボタンをタップ**の
3手が、現状いちばん速いです。通知のリンク先を物件ページにしてあるのはこのためです。

公式FAQの「電話によるお申込みは受け付けておりません」は、**申込み手続きそのものが電話では
完結しない**という意味であって、電話するなという話ではありません。正式な手続きはネットの仮申込みか、
UR営業センターの窓口での書類提出（本申込み）になります。

そして**入居を決めてから動くのでは遅いのです**。UR の手続きは
`お申込み（仮申込）→ 内覧 → 書類提出（本申込）→ 契約 → 入居` の順で、
**仮申込の段階でお部屋の確保が行われる**（[URの借り方](https://www.ur-net.go.jp/chintai/rent/)）。
実際に部屋を見るのは押さえたあとなので、電話の時点で入居を決めている必要はありません。
とりあえず押さえて内覧の予約を取り、見てから考える、という順番が制度上そうなっています。
迷っているあいだに他の人が押さえてしまえば、見ることすらできません。

ただし**お申込みは一世帯につき一件**で、複数の部屋を同時には押さえられません。
押さえたあとは、内覧と書類提出が翌日から1週間以内、契約が10日以内という期限がつきます。

> 出典：[UR賃貸住宅 よくあるご質問](https://www.ur-net.go.jp/chintai/faq/)、
> [空室情報お届けサービス](https://www.ur-net.go.jp/chintai/akishitsu/)（いずれも2026年8月時点）。
> 制度は変わることがあるので、実際に動く前に公式で確かめてください。

- **本番実行は GitHub Actions（Linux）のみ**。PCの起動状態に関係なく動きます。
- **開発は Windows / macOS / Linux のどこでもできる**。OS固有の処理は持たず、
  Chrome の場所の違いだけ `detect_chrome_path()` で吸収しています。
- Claude Code on the web でも開発できる（[設定手順](#claude-code-on-the-web-で開発する場合)）。

## このリポジトリを使う方へ

個人的に作って個人的に使っているツールを、そのまま公開しています。
同じことをしたい方はご自由にどうぞ。ただし次の前提でお願いします。

- **セットアップはご自身で。** 手順は下記に書いてありますが、個別のサポートは行いません
- **自己責任でお願いします。** 動作を保証するものではなく、利用によって生じた不利益について作者は責任を負いません（[MIT License](LICENSE)）
- **`config.json` は作者の設定例です。** `groups`（監視する URL と通知条件）は
  ご自身の条件に置き換えてください。そのまま動かしても作者が見ている物件を追うだけになります
- **Slack Webhook は含まれていません。** ご自身で用意してください
- **公開リポジトリでフォークすると、設定は誰でも読めます。** `config.json` の
  `groups`（＝狙っている物件）はリポジトリを見れば分かります。**取得した部屋そのもの
  （物件名・家賃・間取り）はリポジトリに置いていません**（下記「一覧をリポジトリに
  置かない理由」を参照）。狙っている物件すら知られたくない場合はプライベートに
  してください（その場合 Actions は無料枠の消費対象になります）

UR のサイトへアクセスするツールです。`robots.txt` を確認し、URL間に待機を入れ、
**動きのある時間帯（08:00〜21:00 JST）だけ**5分間隔で動かしています。夜間は動かしません。
監視URLは4本なので UR へのアクセスは平均して**75秒に1回程度**で、
人がひとつの検索結果ページを開いて絞り込みを何度か押すのと変わらない量です。
UR の `robots.txt` に `Crawl-delay` の指定はありません（2026-08-28 時点）が、
**取得間隔をこれ以上詰めるような改変はしないでください。** 相手のサーバーに
負荷をかける使い方をされると、この方法自体が使えなくなります。

## 仕組み

- 08:00〜21:00 JST・5分間隔で `.github/workflows/monitor.yml` が実行される（1日168回）
  （間隔を守っているのは Cloudflare Workers 側です。GitHub の `schedule` は保険と心拍のみです。
  下の「実行間隔は設定どおりにならない」を参照）
- `config.json` の `groups` に並べた URL を巡回してスクレイピング
- 希望順位の高いグループに合致する新着があれば Slack へ通知
- 実行結果（前回の状態と一覧 HTML）は Cloudflare Worker の KV へ置きます。**リポジトリには
  戻さない**（Actions のランナーは毎回まっさらでファイルが残らないため、どこかに預ける
  必要はあります。GitHub ではなく Cloudflare にしている理由は下記）

## ファイル構成

```
ur_monitor.php        監視スクリプト本体。処理はすべてここにある
config.json           監視URL・通知条件・セレクター。振る舞いはここで決まる
composer.json / .lock 依存は chrome-php/chrome のみ

docs/                 ＝ GitHub Pages の公開ディレクトリ。置いたものは全部 Web に出る
  index.html          サイトの入口（資料への案内）。**空き部屋一覧はここに置かない**
  setup.html          セットアップ手順書
  .nojekyll           Jekyll の変換を止める空ファイル。消さないこと

trigger/              起動トリガー（Cloudflare Workers）
  worker.js           稼働時間帯に5分おきで workflow_dispatch を叩く。監視処理は持たない
  wrangler.toml       cron の設定
  README.md           セットアップ手順

tools/
  cloud-setup.sh      Claude Code on the web 用のセットアップスクリプト（開発用）

.github/workflows/
  monitor.yml             本番実行（Cloudflare から起動。schedule は保険と心拍）
  verify-cloud-setup.yml  cloud-setup.sh の検証（手動実行のみ）
```

処理を1ファイルにまとめているのは、フォークした人が中身を1ファイルで追えるようにするためです。
テストスイートが無いので、ファイルを跨いだ整合性を気にせず読める形を優先しています。

## 開発（Windows / Mac 共通）

```bash
composer install
php ur_monitor.php --dry-run
```

`--dry-run` はスクレイピングだけ行い、**Slack 通知も state / 一覧の更新もしない**。
`STORE_URL` / `STORE_TOKEN` が未設定なら保管先を使わずローカルのファイルに落ちるので、
**開発中は秘密情報なしでそのまま動きます**。
本番の状態を壊さずに手元で動作確認できるので、開発中は基本これを使います。

`--dry-run` を付けずに実行すると本番と同じ動作になります。`STORE_URL` / `STORE_TOKEN` を
設定していれば**本番の保管先を直接書き換える**ので、手元では設定しないでください。

| コマンド | 用途 |
|---|---|
| `php ur_monitor.php --dry-run` | 開発用。副作用なしで動作確認 |
| `php ur_monitor.php` | 本番と同じ動作（通常はローカルで実行しない） |
| `php ur_monitor.php --setup` | セレクター確認。ブラウザを表示し `debug_page.html` と `debug_*.png` を保存 |
| `php ur_monitor.php --check-robots` | robots.txt の確認のみ |

### Claude Code on the web で開発する場合

サンドボックスは Ubuntu 24.04 で、**PHP 8.4 と Composer は導入済みですが Chrome は入っていません**。
また既定のネットワーク設定では UR のサイトに到達できません。次の2つを claude.ai/code の
環境設定ダイアログで設定します（**リポジトリにファイルを置くだけでは効きません**）。

**1. Setup script 欄**に [`tools/cloud-setup.sh`](tools/cloud-setup.sh) の中身を貼り付けます。
Chrome for Testing の導入と `composer install` を行います。最後に「セットアップ結果」の
まとめを出すので、`NG` があればセッション開始時点で気づける（このスクリプトは
途中で失敗しても止まらないため、まとめを見ないと後の dry-run が原因不明の0件になります）。

**2. Network access を Custom** にし、許可ドメインへ次の2行を追加したうえで、
`Also include default list of common package managers` を有効にします。

```
ur-net.go.jp
*.ur-net.go.jp
```

ドメイン指定は完全一致のため、実際にアクセスする `www.ur-net.go.jp` は
`ur-net.go.jp` の1行だけでは許可されません。`*.` の行が www を拾います。

既定の **Trusted** は npm や Packagist などの配布元しか許可しないため、そのままだと
コードの編集はできてもスクレイピングの動作確認ができません。なお Chrome を
`dl.google.com` から取らず Chrome for Testing を使っているのも、前者が Trusted の
許可ドメインに含まれないためです。

許可ドメインを設定しても Chrome だけが `ERR_CONNECTION_RESET` になり全 URL が 0 件になる場合、
サンドボックスのプロキシと Chrome の間で TLS 1.3 のハンドシェイクが落ちている可能性がある
（`curl` や `check_robots_txt()` の `file_get_contents()` は通るのに Chrome だけ届かないのが目印です）。
その場合は `config.json` に次を足すと通ります。プロキシを挟まない本番では不要です。

```json
"chrome_flags": ["--ssl-version-max=tls1.2"]
```

この手順は `.github/workflows/verify-cloud-setup.yml` で検証できます。同じ Ubuntu 24.04 上で、
ランナーのプリインストール Chrome を退避してからスクリプトを実行し、入れた Chrome だけで
スクレイピングが通るかを確認します。ネットワーク設定はサンドボックス固有のため対象外です。

### Chrome の場所

通常は自動検出されるので設定不要です。Windows の `Program Files` 配下、
macOS の `/Applications/Google Chrome.app`、Linux の `/usr/bin/google-chrome-stable` などを順に探します。
見つからない環境では `config.json` に `chrome_path` を書けば優先されます。

### Chrome の起動フラグ

通常は設定不要です。実行環境の都合でどうしても Chrome の起動オプションが必要な場合のみ、
`config.json` に `chrome_flags` を書くと既定のフラグの後ろに追加されます。
同じフラグを指定した場合は後勝ちで `chrome_flags` 側が使われます。

```json
"chrome_flags": ["--ssl-version-max=tls1.2"]
```

`--` で始まらない要素は無視されます。本番（GitHub Actions）では空のまま使います。

### セレクターの調整

URサイトのHTML構造が変わって0件になった場合：

1. `php ur_monitor.php --setup` を実行
2. 生成された `debug_page.html` をブラウザで開いて構造を確認
3. `config.json` の `selectors` を更新

## セットアップ手順書の公開（GitHub Pages）

`docs/setup.html` は GitHub Pages で公開しています。**ワークフローもトークンも不要**で、
`main` に push すれば自動で反映されます（反映まで最大10分程度）。

フォークして自分の手順書を公開したい場合は、リポジトリの
Settings → Pages → Build and deployment を次のように設定します。

| 項目 | 値 |
|---|---|
| Source | Deploy from a branch |
| Branch | `main` |
| Folder | `/docs` |

公開 URL は `https://<ユーザー名>.github.io/ur-monitor/setup.html` になります。

`docs/.nojekyll` は Jekyll による変換処理を止めるための空ファイルです。HTML をそのまま配信させます。
これが無いと、HTML 内の `{{ }}` や `{% %}` が Jekyll のテンプレート記法として解釈されて壊れたり、
アンダースコアで始まるファイルが無視されたりします。**消さないでください。**

**GitHub Free では公開リポジトリのみ**この機能を使えます。private のままにしたい場合は
Web 公開を諦め、Slack 通知だけを使ってください。

## 設定（config.json）

振る舞いはすべて `config.json` で決まります。監視対象も通知条件もセレクターも設定側にあるので、
**コードを触らずに変えられます**。

| キー | 必須 | 意味 |
|---|---|---|
| `groups` | ✓ | 希望順位ごとの監視対象。**ここに並べた URL に出てくる物件だけが監視対象**になり、グループごとに通知するかを決める |
| `jitter_max_seconds` |  | 実行開始前のランダム待機の上限秒。`0` で無効。既定 40 |
| `zero_streak_limit` |  | 怪しい結果を何回連続で見たら受け入れるか。既定 18。**時間ではなく回数**なので、実行間隔を変えたら必ず合わせる |
| `shrink_guard_ratio` |  | 前回比でこれを下回る件数を「怪しい」とみなす。既定 0.7。**勘で緩めない** |
| `stale_warning_hours` |  | 実行がこの時間ぶん空いたら Slack に警告。既定 3 |
| `monitoring_hours` |  | 稼働時間帯 `[開始時, 終了時]`（JST）。既定 `[8, 21]`。UR の営業時間を余裕をもって包む値で、**狭めると取りこぼす** |
| `docs_base_url` |  | 資料ページの公開先。一覧の上部メニューからここへリンクします。**空なら資料へのリンクを出さない**（一覧は Worker から配るので、相対パスだと行き先が無い） |
| `selectors` |  | UR ページの CSS セレクター。省略時はコード内の既定値が使われる |
| `slack_webhook_url` |  | Slack の Webhook URL。**環境変数 `SLACK_WEBHOOK_URL` があればそちらが優先**。実値は書かない |
| `chrome_path` |  | Chrome 実行ファイルのパス。省略時は自動検出 |
| `chrome_flags` |  | Chrome の追加起動フラグ |

### groups

**入居したい物件ほど上に置いてください。** グループごとに「通知するか」「どの間取りなら
通知するか」を決められるので、*本当に入りたい物件だけ Slack を鳴らし、
相場を知りたい地域は一覧に出すだけ*にできます。

```json
"groups": [
  {
    "name": "第一希望",
    "notify": true,
    "madori": ["1LDK", "2DK"],
    "urls": ["https://www.ur-net.go.jp/chintai/kanto/saitama/50_3030.html"]
  },
  {
    "name": "参考",
    "notify": false,
    "madori": [],
    "urls": [
      "https://www.ur-net.go.jp/chintai/kanto/saitama/area/208.html",
      "https://www.ur-net.go.jp/chintai/kanto/tokyo/area/222.html"
    ]
  }
]
```

| キー | 意味 |
|---|---|
| `name` | グループ名。**そのまま Slack 通知と公開ページの見出しになる**ので、自分に分かる言葉でよい |
| `notify` | `true` で通知します。`false` なら一覧に出すだけで黙っています。省略時は `true` |
| `madori` | 通知する間取り。**どれか1つに合えば通知**。`[]`（または省略）なら間取りを問わない |
| `urls` | 巡回する UR のページ。何本でも書けるが、増やすほど1回の実行時間が延びる |

**URL は、自分が見ているページをそのまま貼ればよいでしょう。** 次のどちらでも動きます。

- **団地ページ** — `https://www.ur-net.go.jp/chintai/kanto/saitama/50_3030.html` のような、
  ひとつの団地の空室が並ぶページ。**入りたい物件が決まっているならこれが確実**で、
  建物名を文字で書く必要がないぶん、書き間違いで取りこぼす余地が無い
- **検索結果ページ** — `.../area/208.html` のような、エリアや駅で絞り込んだ一覧。
  「この辺で何か出たら見たい」という探し方に向く

**同じ部屋が複数のグループに出てきたときは、上のグループが勝ちます。** 団地ページを第一希望に、
その団地を含む地域ページを参考に置いても、その団地の部屋は第一希望として通知されます。
だから「本命の団地ページ＋周辺の地域ページ」という並べ方をそのまま書いてよいでしょう。

間取りの照合は**部分一致**です。`"2DK"` は `2DK / 51㎡ / 4階` に一致するが、`2LDK` には一致しません。

#### 旧形式（search_urls + watch）

以前の形式もそのまま動きます。`groups` が無いときだけ読まれます。

| キー | 意味 |
|---|---|
| `search_urls` | 巡回する URL。全部ひとつのグループとして扱われる |
| `watch` | 通知する条件。`building`（建物名）と `madori`（間取り）の組で、**どれか1つに合致すれば通知** |
| `notify_all_new` | `true` で `watch` に関係なく全新着を通知。既定 `false`（スパム防止） |
| `highlight_keywords` | 公開ページで強調表示する文字列。**通知には影響しない**（見た目だけ） |

```json
"search_urls": ["https://www.ur-net.go.jp/chintai/kanto/saitama/area/208.html"],
"watch": [
  { "building": "プラザシティ新所沢　けやき通り", "madori": "1LDK" },
  { "building": "プラザシティ新所沢　けやき通り", "madori": "2DK" }
]
```

こちらも照合は**部分一致**なので、次の2点に注意します。

- **空文字は「その条件を問わない」**。`"madori": ""` なら建物名だけで判定します
- **短く書くと巻き込みます**。上の例で全角スペースを外して `"プラザシティ新所沢けやき通り"` と
  書くと「けやき通り第二」「けやき通り第三」まで一致してしまう

**建物名を文字で書く必要があるのが旧形式の弱点**で、`groups` で団地ページを直接指定すれば
この書き間違いの問題自体が無くなります。新しく設定するなら `groups` を使うほうがよいでしょう。

### selectors

UR のサイト構造が変わって0件になったときに直す場所です。手順は
[セレクターの調整](#セレクターの調整)を参照してください。省略すればコード内の既定値が使われるので、
**問題が起きていないうちは書かなくて構いません**。

## Slack 通知の設定

Webhook URL は**リポジトリに置きません**。GitHub Secrets から環境変数で渡しています。

- リポジトリの Settings → Secrets and variables → Actions で `SLACK_WEBHOOK_URL` を登録
- ローカルで通知まで試したい場合は環境変数として渡す：
  - Mac/Linux: `SLACK_WEBHOOK_URL=https://... php ur_monitor.php`
  - Windows (PowerShell): `$env:SLACK_WEBHOOK_URL="https://..."; php ur_monitor.php`

環境変数が未設定なら `config.json` の `slack_webhook_url` を見るが、
**そこに実際の値を書いてコミットしないでください**（Git履歴に残ると消すのが面倒です）。

## 空き部屋一覧をリポジトリに置かない理由

**一覧も前回状態も GitHub にはコミットしません。** Cloudflare Worker の KV に置き、
閲覧は Basic 認証の内側に限っています。

UR は「[このサイトについて](https://www.ur-net.go.jp/site/guide.html)」で、私的使用と
引用を除く転載を認めていません。そのうえで**「インターネットのホームページに写真等を
コピーして貼り付けることは、その運営者が個人であっても私的使用にはなりません」**と
明示しています。物件名・家賃・間取りを公開ページや公開リポジトリに並べるのは、この線をまたぎます。

事実の羅列に著作物性が及ぶかには議論があり、違法と確定した話ではありません。ただ
**UR 自身がそう書いている以上、白いほうを選ぶ**という判断です。以前は `docs/index.html` を
GitHub Pages で公開していましたが、やめました。

```
GitHub Actions ──> 一覧と state を生成
                     └─ HTTPS で Worker へ PUT ──> KV に保管
あなた ──> Worker の URL ──> Basic 認証 ──> 一覧が出る
```

| 場所 | 何が置かれるか |
|---|---|
| リポジトリ | コード、`config.json`（**監視URLと通知条件だけ**）、資料ページ |
| Worker の KV | **前回状態と一覧 HTML**（＝UR から取ったデータ。認証の内側） |
| Slack | 新着の通知（ワークスペースの中なので公開ではない） |

### 保管先の設定

| 置き場所 | 名前 | 中身 |
|---|---|---|
| Worker の Secret | `API_TOKEN` | 監視ジョブが書き込むときの合言葉 |
| Worker の Secret | `VIEW_USER` / `VIEW_PASSWORD` | 一覧を開くときの ID とパスワード（**英数字で**） |
| Worker の KV 結び付け | `STORE` | 保管庫。**この名前ちょうど**でないとコードが見つけられない |
| GitHub Secrets | `STORE_URL` | Worker の URL（末尾の `/` なし） |
| GitHub Secrets | `STORE_TOKEN` | `API_TOKEN` と同じ文字列 |

パスワードを**英数字に限る**のは、ブラウザが Basic 認証で送る文字コードが規格で
定まっておらず、日本語や記号だと正しく入力しても弾かれる環境があるためです。

### 保管先を用意した直後は1回だけ移送が要る

保管先が空だと「前回は0件」になり、**いま出ている部屋が全部 Slack に飛びます**。
`load_state()` はそれを避けて**中止する**ので、まず移送します。

```bash
php ur_monitor.php --seed-state     # STORE_URL / STORE_TOKEN が必要
```

Actions からは、監視ワークフローを手動実行して `seed_state` にチェックを入れます。
すでに保管先に state があれば上書きせずに止まります。

手元に `state.json` があればその内容を移し、**無ければ空の状態を置きます**。
リポジトリに `state.json` は置いていない（中身が UR から取ったデータそのものなので）ため、
フォークした直後は後者になります。**その場合、次の実行でいま出ている部屋がすべて新着として
通知されます。**

### 資料ページから一覧へのリンク

資料ページ（`docs/*.html`）の上部メニュー左端に「空き部屋一覧」を置いてあります。行き先は
**自分の Worker の URL**（Basic 認証の内側）。資料は生成物ではなく手で書いた HTML なので、
`config.json` の値は使えず、**4ファイルに直接書いてあります**。

```
docs/index.html  docs/guide.html  docs/setup.html  docs/architecture.html
```

フォークしたら `ur-monitor-trigger.<自分>.workers.dev` に置き換えてください。書き換えなくても
**中身は守られます**（作者の Basic 認証に弾かれるだけです）。ただし行き先としては正しくありません。

### 公開しているのは資料だけ

| URL | 中身 |
|---|---|
| `https://<ユーザー名>.github.io/ur-monitor/` | 入口（資料への案内） |
| `https://<ユーザー名>.github.io/ur-monitor/guide.html` | 使い方ガイド |
| `https://<ユーザー名>.github.io/ur-monitor/setup.html` | セットアップ手順書 |
| `https://<ユーザー名>.github.io/ur-monitor/architecture.html` | 技術資料（内部の動き） |

いずれも作者が書いた文章で、UR の内容は含みません。有効化の手順は下記
「セットアップ手順書の公開（GitHub Pages）」と共通です。

生成する一覧 HTML にも `noindex, nofollow` を入れてあります。認証の内側なので本来は
不要ですが、取り違えて公開したときの保険です。

## 取得失敗への対策

ページは開けたのに**0件**や**中途半端な件数**で返ることが実際に起きる（描画完了前に
読み取ってしまうなど）。そのまま受け取ると消えた分が「成約」扱いになり、次に復活したとき
誤った新着通知が飛びます。そのため次の順で守っています。

1. 怪しい結果だったら5秒待って1回取り直す
2. それでも怪しければ前回の状態を維持してスキップ
3. `zero_streak_limit` 回連続で続いたら、実際にそうなったと判断して受け入れる
   （**回数であって時間ではありません**。5分間隔 × 既定18回 = UR 側の不調に約90分耐えます。
   実行間隔を変えたらここも合わせないと、耐えられる時間が同じ割合で変わってしまう）

「怪しい」の判定は `untrusted_result_reason()` にあり、次の2つを見ています。

- **0件**（前回この URL に部屋があった場合）
- **前回より大幅に減った** — 既定は `shrink_guard_ratio`（0.7）を下回ったときです。
  1〜2件の出入りで割合が振れるため、前回5件未満の URL は割合判定の対象外

割合の判定を足したのは、実際に2回起きたためです。

| 日時 | 件数 | 実際 |
|---|---|---|
| 2026-08-22 16:36 | 18 → 12 | 5件が1時間後に復活 |
| 2026-08-24 14:34 | 19 → 7 | 12件が33分後に復活し、**誤った新着通知が飛んだ** |

同じ103回の履歴で本物の減少は 20 → 19 件（95%）だけで、これは誤って捕まえません。
連続回数は `state.json` の `zero_streak` に記録している（0件だけを見ていた頃の名残の名前）。

## 実行間隔は設定どおりにならない

かつては `monitor.yml` の `schedule` に間隔を書いていたが、**GitHub がその間隔で
実行してくれるわけではありません**。`schedule` は負荷状況に応じて遅延し、ときには発火自体が
破棄されます。いま間隔を守っているのは Cloudflare Workers 側で、`monitor.yml` に残した
`schedule` は1日4回の心拍だけです。以下はそう決めるに至った実測です。

30分間隔で運用していたときの実測がこれ（UTC、`schedule` イベントの実行のみ）。

```
02:17 → 03:21 → 04:07 → 05:00 → 05:54 → 06:47 → 07:35 → 08:34 → 09:30 → 10:27
  64分   46分   53分   54分   53分   48分   59分   56分   57分
```

**9時間で18回動くはずが12回**しか動いていませんでした。約3分の1が欠落し、実効間隔は50分前後でした。
この数字は当時のコミット履歴から数えたもので、実行のたびに一覧をコミットしていたため
履歴がそのまま全実行記録になっていました。**いまはコミットしないので履歴からは追えません。**
実行頻度を疑うときは Actions タブの実行一覧を見てください。

**厳密な間隔が要るなら GitHub Actions の `schedule` は向いていません。**
15分間隔に詰めても数日後には**1日2回**まで落ちた（2026-08-27〜28）。試行を増やす程度では
どうにもならないと判断し、**発火は Cloudflare Workers から与える**ことにしました（[trigger/](trigger/)）。

`monitor.yml` に残した `schedule` は1日4回で、外部トリガーが死んだときの保険と、
監視が止まっていないかを見張る心拍を兼ねます。**この4回を「間隔」として当てにしないでください。**

Cloudflare に移したあとの実測（2026-08-28）。15分設定のときは5回連続で15分ちょうど・
毎回同じ秒、5分設定に変えたあとも5分ちょうどで並びました。GitHub の `schedule` で
46〜64分にばらついていたのとは別物になっています。

### 監視が止まったら気づけるようにしてある

外部トリガーの停止、トークンの期限切れ、GitHub の遅延——症状はすべて「黙って止まる」に
なります。実際に4日間気づかなかったことがあります。そのため実行のたびに前回からの空白を見て、
稼働時間帯で `stale_warning_hours`（既定3時間）以上空いていたら Slack に警告を出します。
夜間の停止は正常なので、稼働時間帯の分だけを数えています（`monitoring_gap_minutes()`）。

## 既知の制約
- **公開リポジトリなら Actions は無料枠の対象外（無制限に無料）**。以下はプライベートに
  戻す場合の話です。無料枠は月2,000分で、5分間隔は1日168回・月約5,000回。
  1回あたりの実測は45〜85秒（＋jitter 最大40秒）で、課金はジョブごとに分単位へ
  切り上げられるため **月およそ7,500分**になり、無料枠を大きく超えます。
  **プライベートに戻すなら間隔も戻すこと**（15分なら月約1,700分で収まる）
- **ただしプライベートに戻すと GitHub Pages は使えなくなる**（GitHub Free では公開
  リポジトリのみ）。一覧の Web 公開をやめるか、有料プランにするかの選択になる
- リポジトリに60日間動きがないとスケジュール実行が自動停止する
  （正常動作中はコミットが発生し続けるため、通常は問題にならない）
- `jitter_max_seconds` は 40。以前は 0 でした。GitHub の `schedule` は実行時刻が
  勝手にゆらいでいたのでゆらぎを足す必要が無く、待機時間がそのまま課金対象に
  なるためでもありました。Cloudflare から起動するようになって**毎回きっかり同じ秒に
  発火するようになった**ため、ゆらぎは自分で入れる必要が出ました。公開リポジトリの
  うちは待機時間も無料なので、コスト面の理由も無くなっている
