登場人物は3つ

役割やることやらないこと
Cloudflare5分ごとに GitHub を叩くUR を見ない。データを持たない
GitHub ActionsPHP を動かす箱を用意する時刻を守れない（下記 2 章）
PHP + Chrome取得・比較・通知・書き出し常駐しない。毎回終了する

登場する技術

技術役割
Cloudflare Workers時計。5分ごとに GitHub を叩くだけの小さなプログラムを、Cloudflare のサーバー上で動かす仕組み
GitHub Actionsプログラムを自動実行する仕組み。パソコンを起動しなくても動く理由がこれ
PHP本体の言語。ur_monitor.php の1ファイルだけで動いている
Headless Chrome画面のない Chrome。UR は物件情報を後から JavaScript で表示するため、本物のブラウザで開いて描画を待つ必要がある
Slack Incoming Webhook指定の URL にメッセージを送ると Slack に投稿される仕組み
GitHub Pagesリポジトリ内の HTML をそのまま Web 公開できる仕組み。docs/ に置いたものが push のたびに配信される
GitHub Secretsパスワードや鍵を預ける場所。登録後は本人でも中身を見られない

なぜ時計を分けているのか。GitHub の schedule は設定した間隔で動きません。 30分設定で実測46〜64分、15分設定では1日2回まで落ちました。 一方 workflow_dispatch（外から叩く）は確実に動きます。 「時刻を守るのは苦手、言われたら動くのは確実」という性質の差を利用しています。

1回の実行で何が起きるか

2026年8月28日 15:15 の実行（run #114）の実測です。秒数は実際のログから取っています。

push がぶつかることがあります。前の実行のコミットと重なると弾かれるので、 git fetch → rebase -X theirs → 再push を最大3回試します。 5分間隔・実行62秒なので通常は重なりませんが、手作業のコミットとは重なり得ます。

PHP の中の流れ

なぜ Chrome が要るのか
UR のページは HTML と一緒に部屋情報を返しません。表示したあとに JavaScript が差し込みます。 file_get_contents() で取れる HTML には部屋が1件も入っていないため、ブラウザで描画させる必要があります。

robots.txt は確認して終わりではありません。結果を実際に使って、拒否された URL を飛ばします。 UR の記述は Disallow: /chintai/*/result/?skcs= のように * とクエリを使うため、 前方一致では判定できません。* と末尾の $ を正規表現に直し、クエリを含めた文字列で照合しています。

怪しい結果を弾く3段構え

ページは開けたのに0件や中途半端な件数で返ることが実際に起きます。 そのまま受け取ると、消えた分が「成約」扱いになり、次に復活したとき誤った新着通知が飛びます。

「怪しい」の判定は2つ。0件だけを見ていると足りません。

条件意味
0件（前回この URL に部屋があった場合）取得そのものが失敗した可能性
前回の 0.7 倍を下回った（shrink_guard_ratio）描画の途中で読んだ可能性

0.7 という数字は実測から決めたもので、勘で緩めてはいけません。 103回ぶんの履歴にあった減少事象は5件。そのうち誤検知2件（18→12件、19→7件）を捕まえ、 本物1件（20→19件）を通す値が 0.7 でした。19→7件のときは実際に誤通知が飛んでいます （12件が33分後に復活し、うち11件は元からあった部屋）。

前回5件未満の URL は割合の判定から外しています。 少ない一覧では1〜2件の出入りで割合が大きく振れ、誤って保留してしまうためです。

ログに ... のため前回状態を維持 が出るのは正しく働いている姿で、 直すべき不具合ではありません。

通知するかの判定

項目動き
照合のしかた部分一致（str_contains）。完全一致ではない
空文字を書いたとき「その条件は問わない」の意味になる
notify_all_new既定 オフ。オンにすると条件に関係なく全新着が飛ぶ（スパム防止のため既定オフ）
Webhook URL環境変数 SLACK_WEBHOOK_URL から渡す。設定ファイルに実値を書かない

建物名の全角スペースは意味を持ちます。 「プラザシティ新所沢　けやき通り」の空白は全角（U+3000）で、半角にすると一致しません。 UR のページからそのままコピーするのが確実です。

時刻の扱い（UTC と JST）

ここが一番間違えやすい場所です。稼働時間帯が3か所に書かれていて、単位が違います。

場所書き方単位効くところ
trigger/wrangler.toml*/5 0-12,23 * * *UTCそもそも発火するか
trigger/worker.jsSTART_HOUR / END_HOURJST発火しても叩かずに帰る番人
config.jsonmonitoring_hoursJST空白検知が数える時間帯

monitoring_hours だけずれると、毎朝「監視が止まっていました」と誤警告します。 空白検知がどの時間を数えるかを決めているのがこの値だからです。3か所は必ず揃えてください。

8〜21 という数字自体は、作者が「だいたいこんなもん」で決めたものです。 UR の営業時間から導いたものではありません。ただし後から確かめたところ、 UR大宮営業センターは 10:00〜18:00、住まいセンターは 9:30〜17:30、 実際に新着が現れた時間帯は 09:26〜19:28 で、すべてこの中に収まっていました。 上端の 19:28 は営業終了より1時間半あとなので、「営業時間＋1時間」のような理屈で狭めると取りこぼします。

状態はリポジトリにある

気をつけること理由
ローカルで --dry-run を付けずに実行しない2ファイルが書き換わり、Actions のコミットと衝突する
docs/.nojekyll を消さないHTML 内の {{ }} がテンプレート記法と解釈されて壊れる
監視のコミットに [skip ci] を付けないPages のビルドまで止まる恐れがある
docs/ に開発用ファイルを置かない置いたものは全部そのまま Web に公開される

state.json が壊れていたら、処理を中止します（exit 1）。 空とみなして続けると全部屋が「新着」になり、条件に合うものがまとめて Slack へ飛ぶためです。 取得失敗より誤通知のほうが害が大きい、というのがこのツール全体の判断基準です。

止まったときに気づく仕組み

外部トリガーの停止・トークンの期限切れ・GitHub の遅延は、症状がすべて「黙って止まる」になります。 実際に4日間気づかなかったことがあります。

警告は、実行できたときにしか出せません。 だから GitHub 側の schedule を完全には外さず、1日4回の心拍として残してあります。 外部トリガーが死んだときの保険と、見張りを兼ねています。この4回を「間隔」として当てにしないでください。

項目値どこで決まるか
実行間隔5分Cloudflare の cron
稼働時間帯JST 8:00〜21:55cron ＋ worker.js ＋ config.json（3か所）
1日の実行回数168回14時間 × 12
1回の所要45〜85秒（＋ jitter 最大40秒）実測
開始前のゆらぎ0〜40秒jitter_max_seconds
URL 間の待機3秒コード内で固定
描画待ち件数が1秒安定するまで・最長20秒wait_for_rooms()
取り直しの待機5秒・1回だけ失敗対策の1段目
怪しいと判断する減り方前回の 0.7 倍未満shrink_guard_ratio
粘る回数18回（＝約90分）zero_streak_limit
止まったと判断する空白3時間stale_warning_hours
UR へのアクセス平均 100秒に1回（稼働時間帯のみ）3URL × 168回

zero_streak_limit は「時間」ではなく「回数」です。 実行間隔を変えたら必ずここも合わせてください。実行間隔 × この回数が、 UR 側の一時的な不調に耐えられる時間になります。5分に詰めたとき 6 のままだと、 90分あった耐性が30分に縮みます。

無料枠との関係使用量枠
Cloudflare Workers のリクエスト168回／日10万回／日
Cloudflare の Cron Triggers1本5本／アカウント（有料は250本）
GitHub Actions（公開リポジトリ）—無制限に無料
GitHub Actions（非公開に戻した場合）月およそ7,500分月2,000分 → 大幅超過

非公開リポジトリに戻すなら、実行間隔も戻す必要があります。 また非公開にすると GitHub Pages が使えなくなり（GitHub Free では公開リポジトリのみ）、 一覧ページの公開もできなくなります。

おかしいときにどこを見るか

症状まず見る場所ありがちな原因
通知が来ない・実行が少ないCloudflare の Observabilityトークン切れ（401）、権限不足（403）
いつ動いたか知りたいリポジトリの コミット履歴—（履歴が全実行記録になっている）
全 URL が0件になるまず環境を疑うChrome がそもそも到達できていない
件数が中途半端ログの 前回状態を維持正常動作。3段構えが効いている
実行が赤いActions のログ依存の更新、push の衝突

0件のときに、セレクターより先に環境を疑う理由。 robots.txt チェック OK が出ていても、Chrome が通信できているとは限りません。 robots.txt の取得は PHP が直接行っていて、Chrome を通らないからです。 実際に curl は 200 を返すのに Chrome だけ ERR_CONNECTION_RESET になる環境がありました。 ページ内で location.href を見るのが早く、chrome-error://chromewebdata/ なら 描画待ちの問題ではなく取得そのものの失敗です。
